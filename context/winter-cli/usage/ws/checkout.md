# `winter ws checkout` — adopt a remote feature branch into an env

For the rest of the family, see the [`winter ws` hub](./index.md).

`winter ws checkout ENV FEATURE_BRANCH` connects every non-pinned project worktree to `origin/FEATURE_BRANCH` and force-checks each out onto it — or onto the repo's `origin/<main-branch>` when `FEATURE_BRANCH` doesn't exist locally there (a new branch started from main, created on first push). This re-attaches HEAD onto the worktree's env-named branch (moving it off whatever branch the worktree was parked on, or re-attaching a detached HEAD) and force-moves that branch to the resolved ref — a strictly bigger move than a plain reset when the worktree wasn't already on its env branch. `FEATURE_BRANCH` itself may carry a `{main}` ref token — see [ref tokens](./ref-tokens.md) for the alias set — so `winter ws checkout alpha {main}` resets every repo to its own main branch even when repos disagree on the name. **No network** — like `git checkout` it operates on the remote-tracking refs you already have; run [`winter ws fetch`](./fetch.md) first if you want them fresh.

Starting a branch that doesn't exist anywhere requires `--new`: when `origin/FEATURE_BRANCH` resolves in **no** repo, the whole command refuses (`refused-unknown-branch`) — a ref the local store has never seen is more likely a typo or a missing `winter ws fetch` than a deliberate new branch. Separately, any single repo where neither the feature ref nor `origin/<main-branch>` resolves refuses (`refused-missing-ref`) — a per-repo check that fires even when the branch resolves in other repos, since that repo has nothing to reset to; one refusal still aborts the whole run. Neither ref-resolution refusal is bypassed by `--force`.

Phase 1 also checks each repo for a dirty working tree and for **abandonment** — commits on the worktree's branch that aren't on the branch it's moving *away from*. Two checks run: against the worktree's own current upstream (e.g. `origin/feature-123`, falling back to `origin/<main-branch>` when the worktree isn't connected) relative to HEAD, and — since the force-checkout moves the env branch itself, not just HEAD — against that same fallback relative to the env branch directly, whenever the worktree isn't already on it (e.g. detached). **If any repo is dirty or would abandon work (and `--force` is not set), the whole command refuses with a per-repo report — no connect and no checkout runs anywhere.** Note the comparison is against each repo's *own* upstream, not the target `FEATURE_BRANCH` — the guard protects your unpushed commits, not the target's contents.

`checkout` is env-wide with no repo filter — it connects every non-pinned project worktree in `ENV`. To move a single worktree's branch without touching the rest of the env, use [`winter ws reset ENV/REPO REF`](./reset.md) instead.
